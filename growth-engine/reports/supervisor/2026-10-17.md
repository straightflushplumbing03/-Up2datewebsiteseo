  Run history shows the last run COMPLETED at 06:36:19Z the same morning and **nothing since**.
- **Classification.** **Owner action, correctly detected.** The disable was done by the user
  (source `user`) 12 minutes after the final run completed. No agent did this, and no document
  in the repo records the intent — the strategy log, `KNOWN_ISSUES.md` and memory files stop at
  2026-10-16 and none mentions pausing the daily job.
- **Why the check is nonetheless right to fire.** It encodes the invariant "exactly one enabled

  system it is supervising has no writer. That is exactly the state the owner must know about.
- **Exact fix (owner).** Either re-enable:

  (Supervisor does not edit the script or the automation — Level 2/3 boundary.)

### FAIL 2 — `self_merges` passes while every merge is a self-merge (blind check)

- **Evidence.** The check calls
  `GET /repos/.../pulls?state=closed&per_page=40` and reads `merged_by.login`. That field is
  **absent from the list endpoint**: of 40 closed PRs returned, `merged_by` is present in **0**;
  of 35 merged PRs, `merged_by` is non-null in **0**. The guard
  `if author and merger and author == merger` therefore never fires, and the check reports
  "no self-merged PRs" unconditionally.
- **What is actually happening.** The single-PR endpoint *does* return `merged_by`, and it
  equals the author: PR #63 (and #62, #61, #60, #59, …) were merged by
  `straightflushplumbing03` — the same account that opened them. So the review gate the prompt
  added on 2026-10-16 ("never merge your own pull request") was bypassed on the PRs that landed
  that day. Note the cause is structural: agent and owner share one GitHub account, so *every*
  merge by the owner also looks like a self-merge. The check cannot distinguish "agent merged
  unreviewed" from "owner merged", which is precisely the gap a second collaborator account
  closes.
- **Classification.** **Real blind spot (metric defect), plus a real policy event it failed to
  surface.** The PASS is not trustworthy.
- **Exact fix (recommend; do not implement on a supervision run).** In `check_self_merges`,
  drop the list-endpoint field and either (a) fetch each merged PR individually
  (`GET /pulls/{n}`) to read `merged_by`, or (b) treat `merged_by` absent as `UNMEASURED`
  rather than PASS. Then re-run against PRs #59–#63 to see the true count. Also flag that the
  review gate is unenforceable until a second collaborator exists.

### FAIL 3 — `change_volume` 292 files / 268 HTML additions is a metric bug (false positive)

- **Evidence.** For the window, `git log --since=... --numstat` yields **13 commits, 292
  numstat rows, but only 148 unique paths** — 144 rows are the same path counted again through
  merge commits. The script counts *rows*, not distinct files, so `files` is inflated ~2×.
  Worse, `html_touched` counts any row with `added > 0` and a `.html` suffix — i.e. a
  **one-line edit** to an existing page is scored as an "HTML addition".
  `git log --since=... --diff-filter=A --name-only` returns **0 new `.html` files** in the
  window; the only genuinely new files are
  `.github/workflows/verify.yml`, `growth-engine/tests/test_ga4_tag.py`,
  `scripts/add_ga4_tag.py`, `scripts/csp_policy.py`.
- **What actually happened.** PR #63 ("Replace GA4 measurement ID", merged 2026-10-16T06:02Z)
  touched ~141 files, nearly all one-line metadata edits, and PR #61 double-counted the same
  set. A planned, owner-reviewed content push — not runaway writing. The window opens at
  02:54:30Z, so it captures the whole push.
- **Classification.** **Noise / wrong metric.** The agent did not write too much; the metric
  cannot tell an edit from a new page, and double-counts merges.
- **Exact fix (recommend; do not implement).** In `_parse_numstat`: de-duplicate by path
  (`len(set(paths))`) and count a page as "added" only via `--diff-filter=A` (or by checking
  the file is new), not by `added > 0`. Keep `MAX_CHANGED_FILES=120`; the corrected figure for
  this window is 148 unique paths / 0 new pages, which is at the edge of the file budget but
  well inside the page budget — worth saying so rather than failing.

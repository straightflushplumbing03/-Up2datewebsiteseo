# 2026-10-16 — daily detail

## Automation deploy drift (root cause of a whole class of confusion)

**The repo prompt is not the deployed prompt.** The live `SFPL AI Headquarters Daily`
prompt is built by `ai-headquarters-blueprint/build_payload.py` (regex-extracts the text
between `## THE PROMPT` and `## END OF PROMPT` from `01-MASTER-AGENT-PROMPT.md`) and
POSTed to `POST /api/automation/v1/preset/prompt`. OpenHands then **stores a copy**.
Editing the markdown changes nothing at run time. Deploy with
`python3 ai-headquarters-blueprint/build_payload.py --deploy` (PATCHes the stored prompt).

Cost of not knowing this: an earlier edit to
`growth-engine/automations/intelligence-hq-daily.prompt.md` had zero runtime effect —
that file belongs to a **retired** automation (`5dc89b41-6880-40e6-950c-14a635f7bd62`,
now 404). The live id is `1485d659-8663-4776-a507-db0fefed8483`.

## Verification technique that found it

Comparing repo file to live API, not trusting either:

```bash
# live prompt != repo file? compare length and rare lines
curl -s "$HOST/api/automation/v1/$ID" -H "Authorization: Bearer $OPENHANDS_API_KEY" \
  | python3 -c "import json,sys; p=json.load(sys.stdin)['prompt']; print(len(p))"
# then score each .md by shared long lines to find the real source
```

Live prompt was 32,937 chars vs the file I had edited (12,165). The blueprint
(01-MASTER-AGENT-PROMPT.md) shared 317/321 long lines with the live prompt.

## Drift bug in build_payload.py

Hardcoded `"schedule": "0 6 * * *"` while the live job ran `0 6 * * 1,3,5` (Mon/Wed/Fri,
changed in place 2026-10-16). A re-deploy to pick up a prompt edit would have silently
reverted the schedule to daily and **doubled the run count** — the exact "two runs racing
on the same branch names" failure `automations/README.md` warns about. Fixed: constants
`SCHEDULE/TIMEZONE/TIMEOUT/AUTOMATION_ID` used by the payload, `--deploy` opt-in flag.

## Environment gotchas

- `git push` prompts for a password when the remote URL's embedded token is stale. Fix:
  `git remote set-url origin "https://${GITHUB_TOKEN}@github.com/OWNER/REPO.git"`. Always
  set `GIT_TERMINAL_PROMPT=0` so it fails fast instead of hanging.
- The terminal tool rejects a single call containing multiple heredocs / command blocks;
  chain with `&&` or run separately. Heredocs with `(1)`/`(2)` in the text get misparsed —
  put long commit messages in a file and use `git commit -F`.
- `coverage` installs to `~/.local/bin` (not on PATH); use `python3 -m coverage`.
- `seo_audit.py` output is **not deterministic** — `Counter.most_common()` ties reorder
  between runs. Compare as a sorted multiset, never a raw diff.

## KEY discovery: the automation IS the owner's GitHub account

`GITHUB_TOKEN` in the automation authenticates as **`straightflushplumbing03`** — the same
account the owner uses, and the repo's **only collaborator**. Consequences:

- A review request to `straightflushplumbing03` is rejected:
  `422 "Review cannot be requested from pull request author."` The owner account cannot
  review the agent's own PR.
- Branch protection cannot require "a different account approved" when there is only one
  account. So the review gate is **the agent's instruction + the owner's manual merge**,
  not a platform-enforced rule, until a **second collaborator account** is added.
- The policy asks for Copilot review (`copilot-pull-request-reviewer[bot]`) as the available
  automated reviewer, and names the PR in the run summary.
- The GitHub MCP tool's token can't PATCH a PR body (`403 Resource not accessible by
  personal access token`); use `$GITHUB_TOKEN` via the REST API directly instead.

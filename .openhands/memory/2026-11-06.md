## Real defects found by writing tests (all fixed)

1. **`deriveOpportunities` counted pre-existing opportunities as created.**
   `createOpportunity` returned the existing row's id for a duplicate dedupe key,
   so the daily report/activity overstated new work. Now returns `null` on dedupe.
2. **Entity consistency summed ALL history.** `dashboardSummary` used
   `SELECT SUM(matches), COUNT(*) FROM entity_facts` — one historical mismatch
   dragged the figure down forever (26/27 = 96.3% even after the site was fixed).
   Fixed to `WHERE ts = (SELECT MAX(ts) FROM entity_facts)` → now 100%.
   **General lesson: an aggregate over an append-only history table is almost
   always the wrong measurement.** Ask "latest snapshot or all-time?" first.
3. **Removed sections were orphaned.** `persistPages` upserted sections but never
   deleted ones that disappeared from the page, so a deleted section kept a row
   and kept consuming a `geo_scores` row → inflated "sections scored".
   Now `DELETE ... WHERE page_id=? AND ordinal NOT IN (...)` after each crawl.
   (FK `ON DELETE CASCADE` on geo_scores.section_id cleans the scores.)
4. `research.ts` — `ResearchNote` not assignable to `Record<string, unknown>`.
5. `initDb is not a function` in tests → tests use `getDb()` (schema applied
   idempotently on first connection; there is no separate initDb export).

### Free hosting answer (all quotes from the providers' own docs)
- **Fits free:** Oracle Cloud Always Free (real VM + block volume, "for the life

## Oracle deploy path: found a silent wrong-answer bug

Writing the deploy script surfaced a bug that no amount of reading the code would
have caught — **only running it from a copy did.**

- **`REPO_ROOT = process.cwd()/..`** — so deploying `geo-lab/` on its own made
  `crawlRepo()` walk *its own parent directory*. From `/tmp/deploytest` it
  reported **51 pages, entity consistency 0%, 0 competitors, 283 issues** vs
  **153 / 100% / 289 / 0** in the real repo. It exited 0 and looked healthy.
  Fixed: `GEO_LAB_SITE_DIR` (default `REPO_ROOT`), and `crawlRepo()` **throws**
  naming that variable when the site dir has no `index.html`.
- `sitemapUrls()` + 3 other lookups had the same `REPO_ROOT`/`SITE_DIR`
  confusion → no sitemap, mis-resolved extensionless URLs, false broken links.
- **Lesson: verify a deploy by running it from an isolated copy.** A wrong
  crawl path produces a confident, plausible, entirely wrong report.
- **The lab needs the WHOLE repo, not just `geo-lab/`** — the website is the
  repo root and the crawler walks the checkout. `bootstrap.sh` clones the full
  repo and asserts `index.html` exists.
- `npm ci --omit=dev` would break BOTH the build (tailwind/postcss are devDeps)
  and the daily job (`tsx` is a devDep). Use a full `npm ci`.
- Also fixed my own test bug: I truncated the error to `split('\n')[0]`, so the
  assertion on the second line failed. My bug, not the guard's.
- 38/38, tsc clean, build ✓, CI green. Commit `d19ab1e`.

fixes it. If a push ever hangs, that is the cause — don't wait for the timeout.

- **`SET ROLE` bypasses RLS for a superuser** — `postgres` sees every row regardless. RLS tests must

- **`psql` was not installed** in this env; the first `verify-migrations.sh` run reported "38 files

  `postgresql-client` (apt) before believing a migration failure.
- `default_create_pr` **422s if the branch is not pushed yet** — push first (the Lab branch had been
  committed but never pushed).
- **Both PRs landed as DRAFTS** (the known tool gotcha) and needed the GraphQL
  `markPullRequestReadyForReview` flip; REST `PATCH {"draft": false}` no-ops.

Chased the `geo-lab-daily.yml` failure from "not configured" to root cause.

**The public website cannot host the lab.** `straightflushplumbingoc.com` resolves to

It is static: `/api/run`, `/api/reports`, `/login` all **404**. The lab is a Next.js app with
SQLite + background jobs — it needs the Oracle VM. Pointing `GEO_LAB_URL` at the site can
never work, no matter how correct the secret looks.

**`geo-lab.straightflushplumbingoc.com` has no DNS record at all.** `NOERROR` with **0 answers**
on A/CNAME/NS/SOA/MX/TXT/AAAA/CAA from 1.1.1.1, 8.8.8.8, 9.9.9.9; local resolver NXDOMAIN.
`NOERROR + 0 answers` = zone exists, name does not — **not** propagation delay. Don't wait it out.

**The workflow itself is correct — proven, not assumed.** Started the lab on :12000 with a real
`openssl rand -hex 32` token and ran the workflow's *exact* curl (bearer, no cookie):
`HTTP 200`, `5/5 steps ok`, 153 pages / 100% entity / 289 competitors. Negatives: wrong token
→ **401**, no token → **401**. So once the VM exists the only variable is the host.

### Reading a secret's shape without reading the secret
GitHub returns **403** for `GET /actions/secrets` (token can't list them), and the run log masks
values as `***`. To diagnose a bad secret, add a temporary step that prints **booleans only**
(`${#U}`, `case` globs for scheme/slash/quote/space, `[^ -~]` for non-ASCII). That is how the
placeholder `GEO_LAB_URL` was caught. Gotchas found while doing it:
- **`secrets` context is NOT allowed in a step-level `if`** → `422 Unrecognized named-value: 'secrets'`.
- Diagnose on a **throwaway branch**, then delete it — never put a debug step on `main`.

### Repo name gotcha
`straightflushplumbing03/-Up2datewebsiteseo` — the name **starts with a hyphen**. A bare
positional arg gets parsed as a flag, so always use `--repo owner/name`. There is **no separate
geo-lab repo**: the lab is a subdirectory of the site repo (deliberate, spec §17).

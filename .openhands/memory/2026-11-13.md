# 2026-11-13 — GEO Lab deploy runbook + the repo rename that broke the GitHub API

## The GitHub repo was RENAMED mid-session — git follows the redirect, the REST API does not

**The single most expensive discovery of the day.** The website repo
`straightflushplumbing03/-Up2updatewebsiteseo` was renamed to
**`straightflushplumbing03/-Up2datewebsiteseo`** (dropped the `p`; id `1326249049`,
unchanged by the rename) while this session was running.

Symptoms, which look like a token-scope problem but are not:

- `git push` **succeeded** — git follows the rename redirect transparently.
- Every REST call to `/repos/<owner>/-Up2updatewebsiteseo` returned **404**, including
  `GET /repos/...`, `GET /repos/.../pulls/153`, and `POST /repos/.../pulls`.
- `gh pr create` / `gh repo view` failed with
  `GraphQL: Could not resolve to a Repository with the name '...'`.
- The repo **still appeared** in `GET /user/repos` with the fresh `pushed_at`, so it was
  clearly reachable — just not at the name in the URL. The API never follows the redirect.

**How to find the new name** when the API 404s but git works:

```bash
curl -s -H "Authorization: Bearer $GITHUB_TOKEN" \
  "https://api.github.com/repos/<owner>/<old-name>"   # 404
# Then resolve by id — the id survives a rename:
curl -s -H "Authorization: Bearer $GITHUB_TOKEN" \
  "https://api.github.com/repositories/1326249049" | jq -r .full_name
```

**Then fix the remote**, because a stale remote URL will bite the next push too:

```bash
git remote set-url origin https://github.com/<owner>/<new-name>.git
git remote set-url --push origin "https://${GITHUB_TOKEN}@github.com/<owner>/<new-name>.git"
```

**Lesson:** when the GitHub API 404s on a repo that git can obviously reach, do not
suspect the token — **check whether the repo was renamed.** Listing the user's repos and
matching on `pushed_at` / `size` finds it in one call. This is a new instance of the
standing "concurrent sessions mutate this repo" hazard: the owner renames repos, not just
branches.

### Cloudflare Tunnel is the free HTTPS bridge (verified against Cloudflare docs)

The bootstrap deliberately binds port 12000 to localhost and says not to open it, so the
VM has no inbound port for TLS. The domain is Cloudflare-managed — nameservers are
`braden.ns.cloudflare.com` / `dara.ns.cloudflare.com` (verified via DoH:

```bash
curl -s -H "accept: application/dns-json" \
  "https://cloudflare-dns.com/dns-query?name=straightflushplumbingoc.com&type=NS"
```

). Two quotes I verified rather than recalled:

- "Cloudflare Tunnel provides you with a secure way to connect your resources to Cloudflare
  without a publicly routable IP address. … a lightweight daemon in your infrastructure
  (`cloudflared`) creates outbound-only connections to Cloudflare's global network."
  — <https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/>
- A public hostname route works on the **free** plan; the only caveat is serving large video
  files. — <https://developers.cloudflare.com/cloudflare-one/faq/cloudflare-tunnels-faq/>

Commands were checked against Cloudflare's package repo page: the official apt recipe
includes `sudo mkdir -p --mode=0755 /usr/share/keyrings` **before** the `tee` (easy to omit),
the tunnel config wants the tunnel **UUID** (not the name) in `tunnel:`, and the service is
installed with `cloudflared service install` then `systemctl start cloudflared`
(`enable --now` is not what the docs show).

## Verification hygiene (recurring trap)

Running `npm run job` / `npm test` in `geo-lab/` creates `geo-lab/node_modules/` and
`geo-lab/.next/`, which contain `.html` files. The repo validators then scan them and report
**false failures** ("sitemap missing indexable page: geo-lab/node_modules/next/…"). They are
gitignored (`geo-lab/.gitignore`), so CI on a fresh checkout never sees them. **Clean them
(`rm -rf geo-lab/node_modules geo-lab/.next`) before running the validators, or the two
"failures" are pure noise.** With them removed: **404 tests OK, `validate_knowledge_base.py`
OK (158 HTML files)**.

### The real failure mode (and why it matters)
Every failing run ends with:

```
GEO_LAB_URL must start with https:// - refusing to send the run token.
##[error]Process completed with exit code 1.
```

That guard only fires when **both** secrets are non-empty — so the secrets **ARE set**,
and the value of `GEO_LAB_URL` is a placeholder/bare host, not a real https URL. The
workflow is behaving correctly (refusing to leak the token over cleartext). So the
diagnosis is not "not deployed" but "**secret set to a non-URL**". Read the step log
before theorising: `GET /actions/runs/<id>/logs` returns a **zip** — use Python
`zipfile`, not `unzip` (not installed in this env).

## The daily job now actually runs (PR #190)
